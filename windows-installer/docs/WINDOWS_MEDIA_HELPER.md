# Windows media helper — current scope

This page describes the dedicated `--media-helper` virtual-media validation path. Physical installation is implemented through a separate partition-installation helper; see [physical installation](PHYSICAL_INSTALLATION.md) and [partition deployment](PARTITION_DEPLOYMENT.md). Statements below about accepting only owned VHDs apply to this media-helper path, not to the ordinary installation wizard. `work` means the selected installer workspace, defaulting to the tool's `work` directory.

The ordinary WPF process starts a separate hidden .NET process for the operation. A non-administrator caller uses the Windows `runas` verb; the helper checks administrator membership. The helper has a dedicated `--media-helper` entry point and does not open the main window.

Current execution accepts only a new work-directory VHD. It never accepts a physical-device path or disk number from the request. `CreateVirtualDisk` creates the file; `AttachVirtualDisk` uses no drive letters and handle lifetime; `GetVirtualDiskPhysicalPath` binds the new device. Capacity, 512-byte sectors and the file-backed virtual bus are reread from the opened raw handle before writes. No physical USB job is currently supported.

The reviewed source includes OS-issued file identity, length, write time and its existing GPT GUID. The child reopens it, checks the final handle path and compares that metadata before target creation. The read handle prevents source replacement/writes during the operation. GPT inspection here checks signature, sector layout bounds and GUID; it is not source authentication or a content checksum.

The shared writer transfers aligned chunks, flushes, rereads every copied byte and compares it directly. Cancellation signals a named event; the parent waits for child cleanup rather than killing it. Partial/cancelled/unverified results are preserved and never advertised as completed media. Retry creates another independent VHD. Failures retain job/status/result files under the operation directory.

Validated on this Windows host:

- New 16 MiB VHD: handle binding, native capacity/sector/bus, 4 KiB raw write/readback and detach.
- Separate admin child: whole 8,120,172,544-byte image write and readback; independent `Get-DiskImage` shows detached.
- Cross-process cancellation: 71,303,168 bytes written, zero verified, cancelled result; independent detached check.
- Actual reviewed file changed: rejected before VHD creation.
- Physical job kind, missing confirmation and insufficient capacity: separate helpers reject before target creation.
- Written VHD: QEMU vpc read-only backing plus independent overlay reaches the real SteamOS installer home; screenshot checked.

The WPF virtual-validation panel invokes the same controller.

Physical USB execution remains pending. Read-only candidate/source/boot/system planning and fresh metadata rebind, plus native locking/dismount on new owned VHDs, are now implemented as described below. Native physical/source-volume handle binding, complete volume discovery, disk replacement/removal/permission/full-space cases, safe final refresh/eject and dedicated USB tests are still required. Normal-user interactive UAC, event access and the new WPF layout still need an active session. Real USB and Windows dual boot are not covered by these VHD checks. Image size/capacity mismatch and interrupted physical media require explicit retry, not claims of restoring erased data.

## Read-only USB review and owned-volume validation (2026-10-13)

The WPF panel lists USB candidates and their refusal reasons, then re-queries before accepting a review. Source-disk, boot/system, offline/read-only, unsupported sector/capacity/health/layout and missing/duplicate hardware IDs are rejected. A changed disk number can be rebound only using the same unique ID and serial with unchanged device/partition metadata. This is a read-only plan, not write authorization. The actual host query found four disks and zero USB candidates; 23 synthetic policy checks passed. Host identifiers remain private logs and are excluded from the package.

Native volume locking accepts only the newly created VHD object. Every opened GUID-volume handle must report exactly one extent on that object's current disk number and within its capacity. All locks succeed before explicit dismount. Closing handles releases acquired locks on refusal, cleanup and completion. Two NTFS volumes on a new 128 MiB VHD verified second-volume busy refusal, release of the first lock, successful dual lock/dismount/unlock and both preserved sentinels after remount. A separate new two-volume VHD then verified a 32 MiB synthetic image raw write and full direct byte readback while both locks were held. Independent Get-DiskImage checks confirmed both VHDs detached. No existing or physical volume was dismounted.

Evidence: `../logs/usb-planning-volume-locks-20261013.json`. Developer CLI: `usb-plan-checks`, `usb-inventory <prepared.img>`, `native-volume-locks`, `native-volume-write <synthetic.img>` (the latter limited to 128 MiB and always creates a new test VHD).

Physical USB execution still requires integration of native device-handle identity/source-volume binding, complete volume discovery, replacement/removal and permission/full-space handling, final refresh/eject, and dedicated hardware acceptance. The physical write button and helper job remain disabled. Normal-user interactive UAC/event permissions and WPF visual layout remain unverified.

Windows documents the lock, dismount and extent APIs in [FSCTL_LOCK_VOLUME](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_lock_volume), [FSCTL_DISMOUNT_VOLUME](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_dismount_volume) and [IOCTL_VOLUME_GET_VOLUME_DISK_EXTENTS](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-ioctl_volume_get_volume_disk_extents). The VHD tests above supply the local execution evidence.

## Failure state, flush evidence and work-volume space (2026-10-13)

Before requesting elevation, the controller checks caller-available work-volume space. The child checks again immediately before creation: full requested VHD capacity, 8 MiB metadata allowance and 64 MiB work reserve. Windows caller-available space includes quota effects; the snapshot does not reserve space against competing writers. Later I/O failures remain failures. See [GetDiskFreeSpaceExW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getdiskfreespaceexw).

Helper cleanup is explicit for success, cancellation and failure. A successful dispose confirms detach; failed constructors/cleanup do not claim confirmed detach, and cleanup failure prevents a complete result. Before-target cancellation records zero bytes and no created VHD. Copy/verify preserves the original error; if final flush also fails, both errors are retained. WPF stages now distinguish review/space/copy/readback and retain the operation directory and written/verified counts in its log.

Seven real validation cases passed: native too-small VHD refusal without changing its preserved bytes; sector-aligned target corruption rejected by ordinary readback; readback cancellation after 4 MiB verified of 16 MiB written; closed native target handle plus failed final flush reported together; separate helper cancellation before creation; parent callback exception signals cancellation and waits for child's 88 MiB partial-copy cleanup; native available-space refusal on a new small NTFS volume (121,724,928 available versus 209,715,200 required). The test does not fill a host volume. Full 8,120,172,544-byte helper write/readback was repeated successfully. Independent attachment queries confirmed all recorded VHDs detached.

Evidence index: `../logs/media-failure-cleanup-20261013.json`. CLI: `native-media-faults <prepared.img>` (source at least 256 MiB; each native fault target is fresh, helper callbacks cancel their independent new VHD). This covers owned virtual devices and source reads, not physical unplugging or in-flight disk-full I/O. Ordinary-user interactive UAC, device/source-volume handles, removal/replacement, final refresh/eject and dedicated physical USB validation remain pending.

## Native device/source binding and complete volume discovery (2026-10-13)

WPF USB recheck now starts a separate administrator metadata helper (`--usb-review-helper`). Its accepted kind is only `usb-native-readonly-review`. It opens the freshly rebound device with GENERIC_READ, checks native disk number, capacity, sector, USB bus and serial, and compares real partition numbers, GUIDs and ranges. The source volume is resolved from the open source file handle with VOLUME_NAME_GUID, then its native extents must name one different disk and agree with Windows metadata. Native GUID-volume enumeration discovers target volumes independently of drive letters/access-path lists. Unknown extent failures prevent review; only a positively identified CD-ROM with unsupported extents is skipped. Fresh Windows metadata and held-handle device/layout are reread before returning. It never locks, dismounts, writes, refreshes or ejects a physical device. The review result is a snapshot, not later write authorization; eventual physical execution needs a new check.

The owned VHD writer uses the same native device-number/capacity/sector/bus parser and source-handle volume exclusion. A newly created blank VHD must expose zero volumes. The VHD volume-lock entry now rejects an omitted/changed volume set before acquiring any lock, discovers all target GUID volumes independently, and rereads native layout after all locks succeed before explicit dismount. This closes the prior subset-list gap.

Ten real owned-VHD checks passed: new empty RAW disk/native zero-volume query; native device and GPT partition match; changed reviewed range refusal; two exact volume extents; actual source on host vs selected VHD; actual source file on the selected target refused; omitted second volume refused before locks; real native virtual bus rejected as USB; independent readonly child refuses non-USB Windows metadata; and complete-volume lock/layout-reread/unlock with both sentinels preserved. This host reports the fresh disk as RAW in MSFT_Disk and empty MBR in GET_DRIVE_LAYOUT_EX. That difference was observed and recorded after the initial equality check failed; only a freshly reviewed RAW disk with no entries/GPT identity admits the empty-MBR representation. GPT/partition checks remain strict. Seven prior native/helper faults also passed after the guard integration, as did a 32 MiB synthetic complete copy/readback. All recorded VHDs were independently confirmed detached.

Evidence: `../logs/native-device-volume-binding-20261013.json`; CLI: `native-binding-checks <prepared.img>`. Physical USB positive review, MBR hardware behavior, normal-user UAC and WPF visual layout are unverified. Actual physical writes, removal/replacement, complete lock integration for physical devices, refresh/eject and dedicated hardware remain pending.
